# π0.5 真机部署过程 · 技术详解

> 本文从**技术实现角度**讲清楚「微调好的 π0.5 模型 → 真机执行」的完整部署过程。
> 覆盖：部署拓扑、服务器端 `predict_server.py` 的逐段拆解、本机控制脚本拆解、方向约定的推导、端到端时序、关键技术决策与排查。
> 读者：想理解"代码到底在干什么"的人，而不是只会照抄命令的人。

## 1. 部署拓扑与数据流

部署是**两端架构**：一台本机（跑机械臂+相机+控制脚本），一台 GPU 服务器（跑模型）。两者通过 SSH 隧道耦合。

```
┌──────────── 本机 (Ubuntu VM) ────────────┐        ┌────── 服务器 (DGX Spark) ──────┐
│  相机 video6/video4 ──┐                  │        │                                │
│  主臂 can0 (7关节)  ──┼→ 控制脚本         │        │  predict_server.py             │
│                       │   run_pi05_robot │        │   ├ 加载 base + LoRA adapter    │
│                       │   eval_pi05_robot│  HTTP  │   ├ 归一化+拼prompt             │
│                       └──→ POST /predict ─┼──隧道──┼→  ├ 模型推理                   │
│                       ←── 50×7动作 ──────┼───────┼──  └ 反归一化→JSON              │
│  主臂 ← send_action   │                  │        │                                │
└───────────────────────┴──────────────────┘        └────────────────────────────────┘
```

**隧道命令**（本机执行，把服务器 `localhost:8080` 映射到本机 `localhost:8080`）：

```bash
ssh -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
    -L 8080:localhost:8080 -p 6022 root@43.155.204.215
```

- `-L 8080:localhost:8080`：本地 8080 → 转发到服务器的 8080。
- `-p 6022`：SSH 用 6022 端口（非默认 22）。
- `ServerAliveInterval=30` + `ServerAliveCountMax=3`：每 30s 心跳、连续 3 次失败即断，防止隧道"假死"。

## 2. 服务器端 `predict_server.py` 逐段拆解

服务器脚本做四件事：**加载模型 → 把状态转成 prompt → 把图像转成张量 → 推理并反归一化**，最后用 FastAPI 暴露 `/predict`。

### 2.1 模型加载（三段式）

```python
_config = PI05Config.from_pretrained(BASE_DIR, local_files_only=True)
_config.device = 'cuda'
_config.dtype = 'bfloat16'
_base = PI05Policy.from_pretrained(BASE_DIR, config=_config, local_files_only=True, strict=True)
policy = PeftModel.from_pretrained(_base, ADAPTER_DIR)   # 套 LoRA 适配器
policy.eval()
```

技术要点：

1. **第一段加载 base**：`PI05Policy.from_pretrained` 加载 π0.5 基座（PaliGemma 2B + gemma_300m + SigLIP），`strict=True` 要求权重字典严格匹配，防止加载残缺模型。
2. **第二段套 LoRA**：`PeftModel.from_pretrained(_base, ADAPTER_DIR)` 把微调出的低秩增量矩阵"并联"到冻结的基座上。**换权重 = 换 `ADAPTER_DIR` 这一行**。
3. **第三段加载 tokenizer + stats**：

```python
tok = AutoTokenizer.from_pretrained(f'{ADAPTER_DIR}/tokenizer')
with open(STATS_PATH) as f:
    _stats = json.load(f)
_state_q01 = np.array(_stats['observation.state']['q01'], np.float32)
_state_q99 = np.array(_stats['observation.state']['q99'], np.float32)
_action_q01 = np.array(_stats['action']['q01'], np.float32)
_action_q99 = np.array(_stats['action']['q99'], np.float32)
```

`stats.json` 提供**训练数据的分位数 q01/q99**（π0.5 用分位数归一化，不是 min/max）。训练和推理必须用**同一套**统计。

### 2.2 状态 → prompt 的精确数学

这是整个部署最容易出错的地方。`state_to_prompt()` 做四步：

```python
# ① 方向翻转
s = STATE_FLIP * state_deg            # STATE_FLIP = -1.0

# ② 分位数归一化到 [-1,1]
s_norm = 2.0 * (s - _state_q01) / (_state_q99 - _state_q01) - 1.0

# ③ 离散化到 256 桶（0~255 整数）
s_disc = np.digitize(s_norm, np.linspace(-1, 1, 257)[:-1]) - 1
s_disc = np.clip(s_disc, 0, 255).astype(int)

# ④ 拼成 prompt
state_str = " ".join(map(str, s_disc.tolist()))
prompt = f"Task: {TASK}, State: {state_str};\nAction: "
enc = tok(prompt, return_tensors='pt', padding='max_length', max_length=200, truncation=True)
```

逐步技术解释：

- **① 为什么翻转**：见第 4 节方向约定的推导。
- **② 分位数归一化**：`2*(x-q01)/(q99-q01)-1` 是把任意度数线性映射到 [-1,1]。用 q01/q99（第 1%/99% 分位）而不是 min/max，是因为分位数对离群点鲁棒。
- **③ 离散化**：π0.5 的核心设计是**把连续数值当成离散 token**（和语言 token 共享词表）。`np.linspace(-1,1,257)[:-1]` 生成 256 个桶边界，`np.digitize` 找到每个值落在哪个桶，减 1 得到 0~255 的整数。
- **④ 拼接 + tokenize**：`padding='max_length', max_length=200` 把所有 prompt 补齐到 200 个 token，`truncation=True` 超长截断。这是 π0.5 固定的输入规格。

**结果**：一个 7 维连续状态，变成了 prompt 里 7 个 0~255 的"词"。

### 2.3 图像预处理链

```python
def decode_image(b64):
    data = base64.b64decode(b64)
    img = Image.open(io.BytesIO(data)).convert('RGB')
    arr = np.array(img, np.float32) / 255.0          # [H,W,3] ∈ [0,1]
    arr = arr.transpose(2, 0, 1)                      # [3,H,W]
    return torch.from_numpy(arr).unsqueeze(0).to('cuda')  # [1,3,H,W]
```

技术要点：

- 本机发的是 **JPEG → base64**，服务器解码回 JPEG → PIL 读成 RGB → 转 float 并 `/255.0` 得到 **[0,1]**。
- **为什么 [0,1] 而不是 [-1,1]**：π0.5 内部 `_preprocess_images` 会自己 `img*2-1` 转 [-1,1] 喂 SigLIP，尺寸内部 `resize_with_pad` 到 224×224。所以脚本层只负责给 [0,1]。
- 转置 `transpose(2,0,1)`：把 OpenCV/PIL 的 `[H,W,C]` 变成 PyTorch 的 `[C,H,W]`，`unsqueeze(0)` 加 batch 维。

### 2.4 推理与动作反归一化

```python
batch = {
    'observation.images.base_0_rgb': front,          # 俯瞰相机
    'observation.images.left_wrist_0_rgb': wrist,     # 腕部相机
    OBS_LANGUAGE_TOKENS: tokens,                      # prompt 的 input_ids
    OBS_LANGUAGE_ATTENTION_MASK: mask,                # attention mask
}
with torch.inference_mode():
    actions = policy.base_model.predict_action_chunk(batch)   # (1, 50, 32)
actions = actions[0, :, :7].float().cpu().numpy()             # (50, 7)
actions_deg = (actions + 1.0) / 2.0 * (_action_q99 - _action_q01) + _action_q01
```

技术要点：

- **图像 key 名必须精确**：`observation.images.base_0_rgb`（俯瞰）+ `observation.images.left_wrist_0_rgb`（腕部）。写错会报「image features missing」。
- **输出形状 (1,50,32)**：50 = 动作块长度（chunk），32 = 动作维度上限。**只有前 7 维是真实关节**（你的任务 7 个关节），后 25 维是 padding，直接 `[:, :7]` 丢掉。
- **动作反归一化**：`(x+1)/2*(q99-q01)+q01` 是 `s_norm` 的逆运算，把 [-1,1] 映射回度数。
- **动作不翻转**：注意与状态相反，动作方向不取负（见第 4 节）。

### 2.5 HTTP 接口规格

```python
class PredictRequest(BaseModel):
    state: list[float]   # 7 关节角（度，本机原始值）
    front: str           # 俯瞰相机 JPEG base64
    wrist: str           # 腕部相机 JPEG base64

@app.post('/predict')
def predict_endpoint(req):
    action_chunk, disc_state, prompt = predict(req.state, req.front, req.wrist)
    return {'action_chunk': action_chunk, 'state_discretized': disc_state, 'prompt': prompt}
```

请求体 JSON：`{"state":[7个数], "front":"<base64>", "wrist":"<base64>"}`。
响应体 JSON：`{"action_chunk":[[50行×7列]], "state_discretized":[7个整数], "prompt":"..."}`。
`state_discretized` 和 `prompt` 是**调试用回显**（方便验证归一化/离散化对不对），真正用的只有 `action_chunk`。

## 3. 本机端控制脚本拆解

### 3.1 相机读取（三个技术点）

```python
def open_cam(idx, w, h):
    cap = cv2.VideoCapture(idx, cv2.CAP_V4L2)
    cap.set(cv2.CAP_PROP_FOURCC, cv2.VideoWriter_fourcc(*'MJPG'))   # ① 强制 MJPG
    cap.set(cv2.CAP_PROP_FRAME_WIDTH, w)
    cap.set(cv2.CAP_PROP_FRAME_HEIGHT, h)
    for _ in range(6):            # ② 预热 6 帧
        cap.read(); time.sleep(0.05)
    return cap

def read_frame(cap, n=5):        # ③ 容错重读
    for _ in range(n):
        ok, frame = cap.read()
        if ok and frame is not None: return frame
        time.sleep(0.05)
    return None
```

- **① 强制 MJPG**：不设 fourcc 时 OpenCV 自动探测可能选错格式，导致 `select()` 超时读不到帧。
- **② 预热 6 帧**：V4L2 相机刚打开时前几帧不稳定，预热让它进入持续流状态。
- **③ 容错重读**：读 5 次，任何一次成功就返回，全失败返回 None（上层跳过本步）。

**注意一个真实差异**：推理脚本（`run_pi05_robot.py`、`eval_pi05_robot.py`）里 front 相机是 **848×480**，而**录制命令**里 front 是 **640×480**。原因是：推理脚本直接 `cv2.read()` 读帧、**没有帧率校验**，848×480 能读（只是实际 15fps）；而录制走 `lerobot-record`，内部有 `_validate_fps` 校验，848×480 报 15fps 不满足 30fps，所以录制必须改 640×480。**两处分辨率不同是历史遗留，不是错误。**

### 3.2 状态读取（7 关节顺序）

```python
JOINTS = ['shoulder_pan', 'shoulder_lift', 'elbow_flex',
          'wrist_flex', 'wrist_yaw', 'wrist_roll', 'gripper']
obs = robot.get_observation()
state = np.array([obs[f'{j}.pos'] for j in JOINTS], dtype=np.float32)
```

`get_observation()` 返回**原始编码器角度（度）**，这里按固定顺序抽 7 个关节，顺序必须和训练数据、模型一致。

### 3.3 动作执行（帧率控制）

```python
chunk = resp.json()['action_chunk']   # (50, 7) 度
for row in chunk:
    action = {f'{j}.pos': float(row[i]) for i, j in enumerate(JOINTS)}
    robot.send_action(action)
    time.sleep(0.033)     # ≈ 30fps
```

- 一个 chunk 50 帧，每帧发一个动作、sleep 0.033s，总共约 **1.65s**。
- `send_action` 内部：`×joint_directions → clip 到 joint_limits → 转弧度 → 按 motor_can_ids 发 CAN 帧`。
- 帧率 30fps 要和训练数据的动作采样率一致，否则模型预测的"时间轨迹"和实际执行对不上。

### 3.4 三个脚本的分工差异

| 脚本 | 用途 | 关键差异 |
|---|---|---|
| `test_predict.py` | 冒烟测试 | **不连机械臂**，发假状态/灰图，验证服务器推理链通 |
| `run_pi05_robot.py` | 单次真机执行 | `--dry-run`（只预测不动）/ `--steps N`（跑几步） |
| `eval_pi05_robot.py` | N 次评估 | 循环 episode，每集人工复位+判定 y/n，累计成功率 |

## 4. 方向约定的技术推导（STATE_FLIP = -1.0）

这是整个部署最微妙的一点。结论：**state 取负喂模型，action 不翻转直接发**。

推导逻辑：

1. **两个方向空间**：
   - 本机驱动：`get_observation()` 返回**原始编码器**（物理量，未套方向）；`send_action()` 输入是**逻辑量**（内部 `×joint_directions`）。
   - 训练数据集：从别的臂格式转换而来，它的 `joint_directions` = **本机驱动的负值**。

2. **状态方向**：训练时模型学到的状态符号 = 训练数据集的符号 = 本机的**负值**。所以喂模型前要把本机读到的状态 `×(-1)` 翻回训练约定。这就是 `STATE_FLIP = -1.0`。

3. **动作方向**：模型输出的动作已经是在训练数据的动作空间里，而训练动作空间和本机 `send_action` 的逻辑量空间**一致**（不需要再翻）。所以动作直接发。

4. **夹爪 -6.0 是尺度不是符号**：`gripper: -6.0` 是"方向 + 传动比缩放"，由 `send_action` 内部消化，脚本层不用管。

**验证方法**：把臂移到**非零位姿**（抬大臂+弯肘），干跑看预测首动作是否≈当前逻辑角度；符号反了就把 `STATE_FLIP` 改成 `1.0`。零位（state≈0）时 `×(-1)` 不变，区分不出方向，所以必须非零位姿验证。

## 5. 端到端一次推理的完整时序（技术视角）

以 `run_pi05_robot.py` 跑一步为例：

```
t0   本机: robot.get_observation() → 7 关节角(度) [~1ms]
t1   本机: read_frame(front/wrist) → 两张 BGR 图 [~30ms]
t2   本机: encode_jpeg(BGR→RGB→imencode jpg q90→base64) [~10ms]
t3   本机: POST /predict，JSON 体 ~100KB [网络+隧道 ~5ms]
t4   服务器: 状态→翻转→归一化→离散化→拼prompt→tokenize [~5ms]
t5   服务器: 两张图 base64→JPEG→[0,1]张量 [~10ms]
t6   服务器: 模型推理 predict_action_chunk [~300-800ms，占大头]
t7   服务器: 动作反归一化 → (50,7) → JSON 响应 [~5ms]
t8   本机: 收到 action_chunk，进入 50 帧执行循环
t9   本机: 每帧 send_action + sleep(0.033)，共 ~1.65s
t10  回到 t0 读新状态（下一 chunk）
```

**关键观察**：推理延迟（t3~t7，主要是 t6）远小于执行时间（t9）。所以当前"分块闭环"（执行完 50 帧再推理下一块）里，推理不卡顿，执行是主体。如果未来要流水线化（边执行边推理下一块），可以并行 t9 和下一块的 t4~t6。

## 6. 关键技术决策点

| 决策 | 选择 | 原因 |
|---|---|---|
| 图像数值范围 | [0,1] | 模型内部自己 `×2-1`，脚本层只管给 [0,1] |
| 图像 key 名 | base_0_rgb / left_wrist_0_rgb | π0.5 固定输入特征名 |
| 状态表示 | 离散 256 桶 token | π0.5 把数值当语言 token |
| 动作维度 | 只取前 7 维 | 输出 (1,50,32)，后 25 维是 padding |
| 精度 | bf16 | 省显存、提速，π0.5 标准 |
| 执行频率 | 30fps（sleep 0.033） | 匹配训练数据动作采样率 |
| 归一化 | 分位数 q01/q99 | π0.5 默认，抗离群点 |
| 通信 | SSH 隧道 + HTTP/JSON | 服务器只监听 localhost，隧道打通 |

## 7. 部署验证方法（从假到真，逐步）

**第 1 层 · 冒烟测试（不碰真机）**：

```bash
python ~/桌面/rebot_bridge/test_predict.py --state "5,-40,-30,10,0,15,20"
```

验证：① 离散化状态在 0~255 合理范围；② prompt 格式正确；③ action_chunk 形状 (50,7)、度数落在 q01/q99 内；④ 真图 vs 灰图动作明显不同（说明视觉生效）。

**第 2 层 · 干跑（连真机但不动）**：

```bash
python ~/桌面/rebot_bridge/run_pi05_robot.py --dry-run
```

验证：读状态、读相机、调服务器全链路通，但**不发动作**。

**第 3 层 · 真机执行（非零位姿，看方向）**：

```bash
python ~/桌面/rebot_bridge/run_pi05_robot.py --steps 1
```

先摆到非零位姿，看预测首动作方向对不对（验证 STATE_FLIP）。

**第 4 层 · 评估**：

```bash
python ~/桌面/rebot_bridge/eval_pi05_robot.py --episodes 10 --steps-per-episode 5
```

## 8. 部署故障排查（技术层面）

| 症状 | 技术根因 | 排查/修复 |
|---|---|---|
| 服务器 500，日志报「image features missing」 | 图像 key 名写错 | 核对 batch 里 key 名 |
| 动作全在边界上/离散状态全 0 或 255 | 状态在训练分布外（如零位） | 属正常；移到工作位姿再试 |
| 动作方向反 | STATE_FLIP 符号错 | 非零位姿干跑验证，改 ±1 |
| `curl localhost:8080/health` 不通 | 隧道没开 / 服务器没起 | 重开隧道、`tail -f server.log` |
| 相机读不到帧 | fourcc 没设 MJPG | 加 `CAP_PROP_FOURCC=MJPG` |
| 录制报 fps=15 | 848×480 只支持 15fps | 录制改 640×480 |
| 服务器 OOM | 模型 + 显存不够 | 检查 bf16、减小 batch（推理 batch=1 已最小） |

## 9. 一句话总结

**部署 = 本机（读状态+拍图，POST 到隧道） + 服务器（加载 base+LoRA，状态翻负→分位归一化→256桶离散化→拼prompt，图像转[0,1]张量，模型推理→动作反归一化） + 本机（30fps 发 50 帧动作）。核心风险全在"接口对齐"：方向符号、归一化统计、图像 key、关节顺序，任何一处不一致，模型输出就废。**
